# Project Roadmap

Этот файл фиксирует практический план развития проекта, чтобы двигаться небольшими итерациями и не распыляться на всё сразу.

Текущий приоритет проекта:

- сначала стабилизировать single-threaded HTTP server core;
- затем ужесточить и упростить публичный контракт;
- только после этого вкладываться в optional-возможности вроде TLS, multithreading и расширенный client API.

## Текущее состояние

Сейчас у проекта уже есть:

- разделённая структура реализации `libs/http/http*.c`;
- публичные заголовки в `include/http/`;
- примеры в `examples/`;
- тесты по типам:
  - `tests/smoke/`
  - `tests/unit/`
  - `tests/integration/`
- `Makefile` с отдельными целями для сборки и тестов;
- базовый integration-контур с реальным запуском demo-сервера и HTTP-проверками.

Но при этом остаются важные ограничения:

- HTTP-контракт местами слишком слабый и не всегда соответствует ожидаемому поведению production-like сервера;
- публичный API обещает больше, чем стабильно реализовано;
- некоторые optional API остаются stub/placeholder;
- packaging/install слой и альтернативная система сборки пока отсутствуют.

## Принципы развития

Ниже приоритеты, которыми стоит руководствоваться при следующих изменениях:

1. Не добавлять новые большие фичи, пока не укреплён базовый серверный контракт.
2. Сначала закреплять поведение тестами, потом менять реализацию.
3. Делать ставку на простую и предсказуемую single-threaded ветку как на основную.
4. Всё, что нестабильно или не доведено, либо убирать из публичного слоя, либо явно помечать как experimental/stub.
5. Сохранять синхронизацию между кодом, `README.md`, `AGENTS.md`, `API_IMPLEMENTATION_STATUS.md` и этим roadmap.

## Этап 1. Ужесточение HTTP-контракта

Это ближайший и самый полезный этап.

Цели:

- malformed request должен обрабатываться предсказуемо;
- неверный HTTP-метод на известном пути должен отличаться от реально отсутствующего маршрута;
- поведение по keep-alive, пустым телам и служебным заголовкам должно быть зафиксировано тестами и документацией.

План работ:

1. Изменить обработку malformed request.
   Целевое поведение:
   - вместо молчаливого закрытия соединения сервер должен возвращать `400 Bad Request`, если это возможно сделать безопасно.

2. Изменить обработку метода на известном пути.
   Целевое поведение:
   - если путь существует, но метод не зарегистрирован, сервер должен возвращать `405 Method Not Allowed`;
   - если путь не существует вообще, сервер должен возвращать `404 Not Found`.

3. Зафиксировать правила ответа.
   Минимально:
   - `Content-Length`
   - `Connection`
   - поведение пустого body
   - поведение на `GET`/`POST` для demo-маршрутов

4. Обновить integration-тесты под новый контракт.

5. После стабилизации поведения обновить `README.md` и `API_IMPLEMENTATION_STATUS.md`.

Результат этапа:

- библиотека будет вести себя как более внятный HTTP server, а не как прототип с неявными ошибочными ветками.

## Этап 2. Расширение и углубление тестов

После стабилизации базового контракта нужно расширить тестовую матрицу.

Цели:

- уменьшить риск регрессий;
- закрепить уже реализованное поведение;
- быстрее локализовать поломки в parser/response/router логике.

План работ:

1. Расширить unit-тесты:
   - дополнительные проверки request/response helper API;
   - проверки граничных случаев `http_response_*`;
   - проверки utility-функций на edge cases.

2. Добавить integration-негативные сценарии:
   - `405 Method Not Allowed`;
   - `400 Bad Request`;
   - keep-alive после нескольких последовательных запросов;
   - повторные запросы на одном соединении;
   - поведение при пустых и частично некорректных входных данных.

3. При необходимости добавить более узкие parser-level тесты.
   Это особенно полезно, если часть request parsing будет выделяться дальше в небольшие внутренние helper-функции.

4. При желании добавить прогон под sanitizers:
   - `-fsanitize=address`
   - `-fsanitize=undefined`

Результат этапа:

- изменения в core-логике будут безопаснее и быстрее проверяться.

## Этап 3. Стабилизация публичного API

Когда базовое поведение уже предсказуемо, нужно привести публичный слой к честному контракту.

Цели:

- убрать расхождения между тем, что объявлено, и тем, что реально поддерживается;
- сократить количество “полу-публичных” и placeholder-элементов;
- упростить понимание библиотеки снаружи.

План работ:

1. Пройтись по `include/http/*.h`.

2. Для каждой функции и структуры решить:
   - это стабильно поддерживаемая часть API;
   - это feature-flag API;
   - это placeholder/stub;
   - это стоит убрать из публичного слоя.

3. Убрать или жёстче документировать нестабильные элементы:
   - поля-плейсхолдеры;
   - неготовые optional API;
   - недоведённые configuration flags.

4. При необходимости упростить имена и layout публичных заголовков.

Результат этапа:

- внешний пользователь будет видеть более честный и компактный API.

## Этап 4. Дополнительная декомпозиция внутренних модулей

После того как контракт и тесты станут крепче, можно продолжать внутреннюю очистку.

Цели:

- уменьшить связанность модулей;
- облегчить поддержку parser/router/response частей;
- подготовить код к дальнейшим изменениям без роста хаоса.

План работ:

1. Сделать границы между parser, response, router, timers более явными.
2. По возможности уменьшить объём общих внутренних структур.
3. Вынести части логики в небольшие helper-функции, если это реально упрощает тестирование и чтение.
4. Сократить количество неиспользуемых или двусмысленных внутренних элементов.

Результат этапа:

- кодовая база станет проще для точечных изменений.

## Этап 5. Сборка, install и packaging

Это уже следующий уровень зрелости, а не срочная задача.

Цели:

- сделать библиотеку проще для внешнего подключения;
- подготовить более стандартный способ сборки и установки;
- облегчить возможный CI/CD сценарий.

План работ:

1. Сохранить `Makefile` как простой локальный entrypoint.
2. Добавить `CMakeLists.txt`.
3. Добавить install target.
4. При необходимости добавить `pkg-config` файл.
5. Развести debug/release режимы более явно.

Результат этапа:

- библиотеку будет проще использовать вне этого репозитория.

## Этап 6. Optional-возможности

Эти темы не должны быть ближайшим приоритетом, пока core не стабилизирован.

Кандидаты:

- monitoring/metrics;
- TLS;
- multithreading;
- client API;
- compression;
- placeholder под HTTP/2.

Рекомендация по приоритету:

1. Monitoring можно развивать раньше остальных optional features, если нужен наблюдаемый сервер.
2. TLS и multithreading лучше не трогать до стабилизации базовой single-threaded модели.
3. Client API стоит либо отдельно проектировать и тестировать, либо пока явно держать вне основного обещанного контракта.
4. HTTP/2 и compression пока лучше считать дальним roadmap, а не ближайшей задачей.

## Ближайший рекомендуемый порядок

Если идти по-настоящему прагматично, ближайшие шаги такие:

1. Сделать `400 Bad Request` для malformed request.
2. Сделать `405 Method Not Allowed` для известного пути с неверным методом.
3. Обновить integration-тесты под новый контракт.
4. Расширить unit/integration тесты вокруг новых ошибок и заголовков ответа.
5. После этого пройтись по `include/http/*.h` и вычистить unstable API.
6. Лишь затем двигаться в `CMake`, install/package слой и optional feature roadmaps.

## Что не стоит делать прямо сейчас

Пока не стоит:

- распараллеливать разработку на TLS, multithreading и client API одновременно;
- добавлять много новых публичных функций без тестового покрытия;
- обещать в документации больше, чем реально реализовано;
- тратить силы на packaging до стабилизации core server contract.
